# Fusio — github.com/apioo/fusio

Fusio is a self-hosted API management platform: a PSX application on Symfony's
dependency-injection container and Doctrine DBAL, whose routes, operations,
schemas, apps and users all live in its own database, with a downloadable
administration interface served from `public/apps/fusio`. Tracker issue
[#777](https://git.modulesgarden.tech/panelalpha/playground/supported-apps/-/work_items/777).

Detection reads the repository correctly on its own — `composer.json` and no
`artisan`, so the `php` strategy, PHP 8.4, the shared Apache base image with
`~/project` bind-mounted, `composer install` on the host. The deploy finished
successfully without this recipe and every request answered **HTTP 500**, which
is the `serving-error_page` verdict it exists to fix.

## What the engine could not infer

**The database was configured, and configured for somebody's laptop.** Most
PHP applications that 500 on a fresh clone are missing a config file. Fusio
ships one, filled in:

```
APP_CONNECTION="pdo-mysql://root:test1234@localhost/fusio"
```

`configuration.php` maps that name onto `psx_connection`, `FrameworkConfig`
parses it with Doctrine's `DsnParser` and opens a DBAL connection on every
request, and a container has no MySQL on its own loopback. `database: mysql` in
`panelalpha.yaml` is the key that fixes it — the engine provisions a database
and user on the account's own MySQL server and passes
`DB_HOST`/`DB_PORT`/`DB_DATABASE`/`DB_USERNAME`/`DB_PASSWORD` into the
container — and `files/panelalpha/fusio-setup.sh` turns those five into the one
DSN Fusio wants, on the install and upgrade stages, before Apache binds. The
credentials are `rawurlencode`d into it, which is exactly what `DsnParser`
`rawurldecode`s back out.

**The committed line has to be deleted before the container starts, not
corrected after it.** The generated compose file carries `env_file: - .env`, so
every line of the repository's `.env` becomes a real process environment
variable — and Symfony's `Dotenv::populate()` skips any name that is already
set. This is the same trap `bolt/core` documents from the other side, where a
secret written to `.env.local` was read, found to be shadowed by the committed
`.env`, and discarded. A DSN corrected from the install stage would lose to the
committed one for the life of the container. So `hooks/prepare.sh` deletes the
`APP_CONNECTION` line outright, before the compose file is even written, and
the setup script appends the real one; the name is then defined in exactly one
place, and Apache and the CLI read the same value.

**`APP_DEBUG=true` is committed too.** `psx_debug` is read straight from it,
and with it on PSX renders the exception message, the file, the line and the
whole stack trace into the response body of every failed request — on a public
URL. The prepare hook turns it off, along with `APP_ENV=dev`.

**`APP_PROJECT_KEY` is a published secret.** The repository commits a real
32-character key, the same one on every clone, and `configuration.php` says in
capitals what it is: the key that encrypts the connection credentials stored in
the database, which must not change after the installation. It is generated per
account and kept in `~/.panelalpha/fusio-project-key` rather than beside the
code — a rebuild re-clones over `~/project` while the database it encrypted
stays exactly where it was. (Not in `$HOME` itself: an account home is
root-owned and `755`, so the account cannot create a file directly in it.
`~/.panelalpha/` is the engine's own per-account directory and is owned by the
account.)

**Nobody can log in to an installation that installed itself.** Fusio has no
installer service and no wizard: the Doctrine migrations under
`Fusio\Impl\Migrations` *are* the installation — tables, categories, scopes,
roles and every default operation — and they seed one internal `Administrator`
row whose password is generated by `TokenGenerator` and told to nobody. That is
why Fusio's own readiness check, `system:check user`, asks for *more than one*
user. The setup script uses that check as its guard and creates the human
account with `system:user_add --role 1 --username … --email … --password …`,
which takes every field as an option and asks nothing.

**Fusio ships no user interface.** The administration app at `/apps/fusio` is a
separate bundle fetched from `api.fusio-project.org` by
`marketplace:install fusio`, which also creates the OAuth2 app row it
authenticates as and rewrites `frameworkConfig->getDispatchUrl()` into its
`index.html`. A CLI run has no `Host` header to guess that URL from, which is
why the setup script writes `APP_URL` into `.env` first (the engine already
passes the same value in the container environment; writing it to the file is
what makes the web requests agree with the CLI). This is the one step that
depends on something outside the host, and it cannot be made fatal anyway —
`marketplace:install` catches its own throwables and exits 0 — so the script
checks for the installed file afterwards and reports how to retry.

**`public/install.php` is a web installer inside the document root.** It is not
an open door: a POST needs a lock file whose name comes from the visitor's own
session, which is a proof-of-ownership check. But it renders a page describing
the installation to anyone who asks, and `README.md` says to delete it once the
install is done. The install is done from the install stage here, so the
prepare hook removes it.

**Readiness.** The engine runs `docker compose up -d` without `--wait` and
probes as soon as it returns, which would be while the migrations are still
running. `overrides/docker-compose.override.yml` gives the app a healthcheck
and adds a no-op `ready` service gated on
`depends_on: app: condition: service_healthy`, which is what makes `up -d`
block. It also raises `mem_limit` to 768m: `ServiceLimits` caps an app-role
service at 384m, and the install compiles a Symfony container over ~200
packages and then runs the migrations in the same process.

Two things this repository does **not** need, which several of its neighbours
do: it commits a `composer.lock`, so `--no-plugins` costs it nothing (its only
`composer-plugin`, `php-http/discovery`, is disallowed in its own
`composer.json`), and it does not require `symfony/framework-bundle` at the
root, so nothing here wants `APP_ENV=prod` from the engine — and nothing in
Fusio reads `psx_env` at all.

## Files

| File | What it does |
|---|---|
| `panelalpha.yaml` | `extends: php`, `docroot: public`, `database: mysql`, and the `fusio-setup` command on the install and upgrade stages |
| `hooks/prepare.sh` | Rewrites the committed `.env` (project key, `prod`, debug off, trusted proxy header), deletes `APP_CONNECTION`, generates the administrator password, removes `public/install.php` |
| `files/panelalpha/fusio-setup.sh` | `APP_CONNECTION` and `APP_URL` from the provisioned database and domain, the migrations, the first administrator, the administration app |
| `overrides/docker-compose.override.yml` | The app healthcheck, the memory limit and the `ready` gate |

## Health probe

The healthcheck asks for two things, and the second is the interesting one:

1. `GET /` — `meta.getAbout`, a public operation that only exists once the
   migrations have inserted it, answered by a router that reads its routes out
   of the database. A 200 means the schema is built and Doctrine can reach it.
2. `GET /system/health` — grepped for `"healthy":true`, not trusted for its
   status code, because the operation answers 200 either way. What it reports
   is a live ping of every connection stored in the database, and those
   connection configs are encrypted with `APP_PROJECT_KEY` — so this is the one
   request that proves the key the deploy generated is the key the data was
   written with.

Both routes are public on purpose. Fusio runs a fail2ban-style firewall
counting client errors per address (`fusio_firewall_maxretry`, 32 in two
minutes, banned for five), and a probe every 10s onto a route that answered 401
would eventually ban the container's own loopback. The same firewall is why the
prepare hook sets `APP_TRUSTED_IP_HEADER=X-Forwarded-For`: without it every
request looks to Fusio like it came from the engine's proxy, and one visitor
mistyping a password enough times would ban every visitor.

## Credentials

`~/project/.panelalpha-admin-password`, mode 0600, generated per account by
`hooks/prepare.sh` and never a default; the copy of record is
`~/.panelalpha/fusio-admin-password`, so a rebuild restores the same password
rather than writing a file that no longer matches the database. The
administrator is `admin` / `admin@example.com` — a hook is told neither the
account's address nor its domain. Override either with `FUSIO_ADMIN_USER` /
`FUSIO_ADMIN_EMAIL` in the project's env vars before the first deploy.

Sign in at `https://<domain>/apps/fusio`.

## Verified on mariusz, 2026-09-20

- Batch run from a clean account: `deploy-ok`, `serving: ok`, HTTP 200, 12 of
  12 health checks pass, 90s with the base image cached (the run that had to
  build it took about fifteen minutes).
- The install stage's own log: the migrations through
  `Version20260829083317`, `created administrator admin <admin@example.com>`,
  `Installed app fusio/fusio`, `installed the backend app at /apps/fusio`.
- A real password login over the public domain, with the generated password:
  `POST /authorization/token`, `grant_type=password`, → 200 with an access
  token whose `iss` is the account's own https URL.
- An authenticated call with it: `GET /backend/account` → 200,
  `"name": "admin"`, role 1, all 57 backend and consumer scopes.
- `GET /apps/fusio/` → 200, and its `index.html` carries
  `FUSIO_URL = 'https://<domain>/'` — the URL substitution the CLI could only
  get right because `APP_URL` was written first.
- Exposure: `.env`, `.panelalpha-admin-password`, `docker-compose.yml` and
  `.git/config` answer 403; `configuration.php`, `provider.php`,
  `container.php`, `composer.json`, `panelalpha/fusio-setup.sh` and
  `install.php` answer 404, all of them being outside `public/`.

Two things worth knowing if this recipe is changed. The first attempt at the
healthcheck grepped for `"healthy":true` and never went healthy: PSX
pretty-prints its JSON whatever `psx_debug` says, so the body reads
`"healthy": true` and the `ready` gate held `docker compose up -d` open until
it timed out — with a perfectly working application behind it. And an earlier
`hooks/prepare.sh` kept its secrets in `$HOME`, which fails the deploy at the
redirection: an account home is root-owned and `755`.

## Not done

- No `overrides/app.sh`: no `info`, `install`, `users:*` or SSO. The material
  is there — `system:user_add` and `system:token` cover creating a user and
  minting a token for it, and the backend API has full user CRUD — so the
  strategy would be "built-in CLI commands", the simplest one. This recipe
  only gets the application deployed, installed and safe.
- Fusio's cronjobs (`system:cronjob_execute`) and the messenger consumer
  (`messenger:consume`, configured as `doctrine://default`) are not scheduled
  or run. Nothing in the default installation needs them, but an account that
  starts using events or webhooks will.
