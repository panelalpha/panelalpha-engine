# Bolt CMS (`bolt/core`)

Symfony 6.4 + Doctrine ORM + Twig, with an Encore-built Vue control panel at
`/bolt`. SQLite by default, so the whole site is `~/project` and one file in
`var/data/`.

```
panelalpha.yaml                          extends: php, docroot: public, the install/upgrade command
hooks/prepare.sh                         everything that has to happen before Composer resolves
files/panelalpha/bolt-setup.sh           the install/upgrade command's body
files/config/packages/panelalpha.yaml    trust the engine's proxy
overrides/docker-compose.override.yml    healthcheck + `ready` gate
```

## Log in

```
user:     admin
password: ~/project/.panelalpha-admin-password     (0600, generated per account)
url:      https://<domain>/bolt
```

The password is generated by `hooks/prepare.sh` on the first deploy and never
rewritten, so an operator who changes it in the control panel keeps their
change. A redeploy re-clones `~/project` and starts the whole site over — see
below. If the file is lost, `bin/console bolt:reset-password admin` inside the
container asks for a new one.

## What it ships with

Bolt's own demo content — the fixtures in `src/DataFixtures/`, minus the
sample-photograph download. That is not decoration: `homepage: homepage` in
`config/bolt/config.yaml` resolves to a *record*, and
`TwigAwareController::renderSingle()` throws `NotFoundHttpException` when there
is none, so a Bolt with an empty database answers 404 on `/`.

The fixtures also create six users — `admin`, `steve`, `jane_chief`,
`tom_admin`, `john_editor`, `eddie` — three of them enabled and three of them
with passwords written in plain text in a public repository (`admin%1`,
`jane%1`, `john%1`). `files/panelalpha/bolt-setup.sh` replaces **every** one of
those passwords before Apache binds: `admin` gets the generated one, the other
five get `bolt:reset-password -n`'s own random default, which nobody records.
They are still there as the authors of the demo content; delete them with
`bin/console bolt:delete-user <username>` once you have replaced the content.

Upstream's way of avoiding the known passwords is `doctrine:fixtures:load
--append`, which switches `UserFixtures` to random ones. It cannot be used on
this branch: `TaxonomyFixtures::load()` returns early when it sees `--append`
in `$_SERVER['argv']`, registers no references, and `ContentFixtures` then dies
in `BaseFixture::getRandomTaxonomies()` on `array_keys(): Argument #1 ($array)
must be of type array, null given`. `bin/console bolt:setup` hits the same
wall.

## Why the recipe exists

The deploy before it ended `serving-error_page`: HTTP 500 on every request,
with a `node` container restart-looping beside it. Six separate causes, four
of which come back to one fact — **`bolt/core` commits no `composer.lock`**, so
what `composer install --no-dev` produces on a hosting account is not the tree
any Bolt developer has ever run.

| What was wrong | Where it is fixed |
|---|---|
| `vendor/autoload_runtime.php` never written, so `public/index.php` and `bin/console` both die on `LogicException: Symfony Runtime is missing` | `bolt-setup.sh` runs `composer dump-autoload` |
| `PackageVersions\Versions` and `ComposerPackages\{Packages,Types}` never generated, and Bolt reads both | same `dump-autoload` |
| four `require-dev` bolt-extensions in the lock but not on disk; `ExtensionRegistry` throws inside a compiler pass | `prepare.sh` takes them out of `require-dev` |
| `config/routes/extension_*.yaml` and `config/services_bolt.yaml` committed, pointing into `vendor/` paths `--no-dev` does not create | `prepare.sh` removes them, `bolt-setup.sh` regenerates them |
| `APP_SECRET=!ChangeMe!`, and a secret in `.env.local` is shadowed by `env_file: - .env` | `prepare.sh` replaces the placeholder in `.env` |
| nothing reads `TRUSTED_PROXIES`, so every absolute URL is `http://<domain>:8000/` | `files/config/packages/panelalpha.yaml` |
| the repository's dev `compose.yml` read as backing services: mariadb, nginx, phpMyAdmin and a crash-looping `node` | `prepare.sh` renames it `compose.yml.upstream-dev` |

`panelalpha.yaml`'s description has the detail; this is the index.

## A redeploy starts over

`GitRepository::cloneConfiguredRepository()` calls `clearContents(~/project)`
before it clones, and Bolt's database is `var/data/bolt.sqlite` *inside*
`~/project`. A redeploy therefore discards the content, the users, the
generated `APP_SECRET` and the password file, and the install stage builds a
fresh site. That is the engine's behaviour for every bind-mounted checkout —
grocy and Heimdall lose their SQLite files the same way — and this recipe does
not try to work around it: moving `var/data` into a named volume would keep the
database while `.panelalpha-admin-password` was regenerated beside it, leaving
a file that confidently states the wrong password.

## Four things for the engine

1. **`PhpHostBuild::mayRunPlugins()` is keyed on `composer.lock`.** A project
   with no lock can never be granted the installer-plugin exemption, however
   obviously it needs it — and `symfony/runtime` is on the exemption list by
   name, so every lockless Symfony 5.3+ project fails the same way. The
   resolved tree, or `composer.json`'s own `config.allow-plugins`, would answer
   the same question after the install.

2. **An app config's `stage: build` command is read and silently dropped.**
   `AppConfig::readManifest()` excludes `commands` from the manifest, and
   `PlatformValues::applyResolvedCommands()` only walks
   `$manifest->stage(BUILD)`, so nothing an app config declares for the build
   reaches `install_command` / `build_command`. Host and container stages work;
   `build` does not, and does not complain.

3. **`env_file: - .env` defeats `.env.local` for every Symfony app.** The
   generated compose file loads the repository's committed `.env` into the
   process environment, and real environment variables beat every dotenv file,
   so the channel Symfony documents for per-install secrets cannot be used: a
   recipe has to edit the committed file instead. Worth a line in the php
   platform's docs at least.

4. **`RuntimeSidecars` keeps too much from a workstation compose file.**
   bolt/core's `compose.yml` yielded `database`, `web` (nginx), `node`
   (`encore dev --watch`) and `padm` (phpMyAdmin) as "runtime services" next to
   the app the `php` strategy builds. A recipe has no key to say "this compose
   file is nobody's stack"; renaming the file is the only lever, and the name
   has to dodge `COMPOSE_FILE_CANDIDATES`, the `.panelalpha-local` stash suffix
   *and* the `compose.*.yml` / `docker-compose.*.yml` template glob.

## Not done

- **No `overrides/app.sh`.** Bolt has the CLI for it —
  `bolt:list-users`, `bolt:add-user`, `bolt:delete-user`,
  `bolt:reset-password` — but `bolt:reset-password` takes no password
  argument, and there is no SSO endpoint to build any of the three patterns on.
  Worth doing; out of scope for making the site serve.
- **Upgrades.** `doctrine:schema:update --complete --force` on every redeploy
  is right for a project with no migrations, and would be the wrong tool the
  day Bolt ships some. `bolt-setup.sh` already stamps the metadata storage so
  that day starts from a clean slate.
