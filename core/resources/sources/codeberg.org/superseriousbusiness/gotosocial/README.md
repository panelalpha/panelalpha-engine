# GoToSocial (codeberg.org/superseriousbusiness/gotosocial)

GoToSocial is a single-binary ActivityPub (fediverse) server implementing the
Mastodon client API: SQLite (or Postgres), a local media store, and an instance
keypair that is the server's federation identity. AGPL-3.0. A personal server, in
scope; not a relay, not a mail-receiving app.

## Image, not source build

Runs the image upstream publishes: `docker.io/superseriousbusiness/gotosocial`.
The checkout contributes only its git ref (to pick a tag); it is not used as a runtime. Two reasons a bare checkout
does not build a runnable server:

1. The repo's **root Dockerfile is a packaging Dockerfile**, not a build: its
   final stage is `FROM alpine:3.21` and `COPY --chown=1000:1000 gotosocial
   /gotosocial/gotosocial` -- it copies a binary goreleaser/build.sh must have
   produced first. On a bare checkout that binary is absent, so a `docker build`
   fails at the COPY. Detection would otherwise pick this Dockerfile (priority
   970).
2. Even a Go build is two-language: `web/assets/dist` is generated by a
   yarn/node pipeline (Dockerfile stage 1) that the engine's `go` strategy does
   not run. (Assets are copied files, not `//go:embed`ed, so the Go compile
   itself would pass -- but the result has no web UI, and the packaging
   Dockerfile above is what detection actually selects.)

So detection is steered to compose: the recipe ships `overrides/docker-compose.yml`,
which `AppConfigBootstrap` writes as the project's `docker-compose.yml` before
detection, and `ComposeUsableProbe` (priority 980) then wins over the root
Dockerfile (970) -- the probe explicitly accepts a repo that also has a root
Dockerfile.

## Federation

GoToSocial bakes the host into every URI and the instance key-id, and other
servers verify HTTP signatures against it, so federation depends on the final,
stable public domain.

## What the recipe supplies

- **GTS_HOST from the public domain.** GoToSocial's `host` is a bare hostname (no
  scheme) baked into every URI and the instance keypair's key-id, so it must
  equal the final public domain and be stable. The engine's `*_URL` placeholder
  rewrite injects a full `https://` URL, not a bare host, so the compose sets
  `PA_PUBLIC_URL: http://localhost` (rewritten to the public https URL because
  the key ends in `_URL`) and `files/panelalpha/gotosocial/entrypoint.sh` strips
  the scheme/port/path to compute `GTS_HOST` before `exec`-ing the server. Fails
  closed: no public URL -> no start (never bakes a localhost identity).
- **Admin before the public port opens.** GoToSocial refuses `admin account
  create` until the server has run once ("instance application not yet created,
  run the server at least once before creating users"). The one-shot `init`
  service (which publishes **no ports**) starts an internal server, waits for
  `/readyz`, stops it, then runs `admin account create` + `confirm` + `promote`.
  `app` declares `init: service_completed_successfully`, so the public 8080 opens
  only after the admin exists. Signup is invite-only
  (`accounts-registration-open=false`), so there is no open self-signup form.
  Idempotent: on a redeploy the admin exists and is left untouched.
- **Data survives redeploy.** SQLite DB, media store and the instance keypair
  (a row in the DB) all live in `~/.panelalpha/gotosocial/storage`, bind-mounted
  over the image's `VOLUME /gotosocial/storage` -- the only directory that
  survives a redeploy (`~/project` is re-cloned) and is account-owned
  (`~` is chowned root each rebuild). Both services run as the account uid/gid
  (written into `docker-compose.override.yml` by `prepare.sh`). The wazero cache
  is redirected under the same dir so nothing lands on an anonymous volume.

## Stack

Three services. `init` (no ports): bootstrap + admin, exits 0. `app`: `gotosocial
server start` behind `entrypoint.sh`, binds 0.0.0.0:8080, `GTS_LETSENCRYPT_ENABLED
false`, `GTS_PROTOCOL https` (engine terminates TLS), healthcheck on the
unauthenticated `/readyz` via the alpine image's busybox `wget`. `ready`: alpine
no-op gated on `app: service_healthy`, because `docker compose up -d` runs without
`--wait`.

## Notes

- Admin username/email/password are passed to `admin account create` as CLI
  flags: despite the config fields being `nocli`, the subcommand marks
  `--username/--email/--password` **required**, so `GTS_USERNAME`/`_EMAIL`/
  `_PASSWORD` env alone panics with "required flag(s) not set". Briefly visible
  in `ps` inside the one-shot init container only.
- GoToSocial's CLI logs to **stdout**, so the admin-existence check runs with
  `GTS_LOG_LEVEL=error` to keep `admin account list` machine-readable.
- The app serves every route itself; there is no document root, so no file
  in the checkout or the storage directory is web-reachable. The instance
  private key lives only in the database; the ActivityPub actor exposes only the
  public key.
- No password grant: GoToSocial allows only `authorization_code` and
  `client_credentials`. A user API token needs the browser OAuth flow.
